# Todoist widget

A separate task list at 2x3, 3x3, 4x3 or 4x5 connected to Todoist with a personal API token. It works without a Widgetify login. The owner approved the light-theme proposal in `design/todoist/assets/proposal.png` before implementation.

## UI

The task-view tabs use the shared TabNavigation with centered labels. Today is the default on each mount and retains unfinished tasks due today or earlier; Tomorrow shows only the next day. Upcoming includes all active tasks, including overdue and undated tasks. The project filter applies in every view. `utils/task-view.ts` uses Widgetify's selected timezone for fixed timestamps and preserves literal all-day and floating dates. The view updates across midnight and clock corrections. A new task in Today or Tomorrow inherits that date; editing an existing task preserves its schedule.

`components/todoist-task-list.tsx` shows Todoist tasks and Google events in a combined timeline, with overdue tasks in a separate section above it. `utils/task-timeline.ts` sorts timed rows by date and clock time, earliest first, using Widgetify's selected timezone. Equal times keep their input order. Tasks without a clock time follow in their existing order, then all-day Google events in calendar order. Timed task labels use the same timezone as sorting. `components/todoist-calendar.tsx` keeps connection, loading, error and empty messages below the list, through the existing Widgetify Google connection. Sign in to Widgetify and connect Google through the offered action; linking Google only inside Todoist does not grant this extension access. Calendar titles open in Google Calendar. Their separate completion circles hide an occurrence in this widget without changing Google Calendar. They do not belong to Todoist projects. Today and Tomorrow show overlapping events for that local day, including all-day and overnight events. Upcoming events cover 30 days; Upcoming tasks have no date limit. `utils/calendar-events.ts` handles overlap, calendar ordering, duplicates, display times and allowed event links. `components/todoist-calendar-event.tsx` owns calendar row markup so it does not bury the task list. Event loading and errors do not hide tasks. The endpoint controls which Google calendars it returns; this widget cannot promise events from additional calendars the backend does not expose.


`todoist.widget.tsx` owns token setup, the project filter, task rows, sync status, connection actions and the editor. The small sync button stays visible and refreshes both Todoist tasks and connected Google events, bypassing the HTTP cache on manual calendar refresh. The new-task button sits directly below the project dropdown and above the list, and hides while an editor is open. The update time uses WidgetHeader.info in the top-left menu slot: it shows at rest, then gives way to the three-dot menu on hover, keyboard focus or an open menu. It no longer appears at the bottom of the scrolling content. `components/todoist-task-list.tsx` owns the rows so their markup does not bury the connection and editor state. Clicking a task opens `components/todoist-editor.tsx` inside the widget; the content scrolls at narrow widths. The shared scrollbar-none utility hides the scrollbar while keeping wheel, touchpad and keyboard scrolling available. All four sizes use the same list and editor; wider sizes give rows more room, and taller sizes show more tasks. The editor supports title, description, an existing project and section, labels, four priorities, a Jalali date picker, time, and recurrence. New tasks default to the filtered project, or Inbox when no project filter is selected. Labels accept comma-separated names. Common recurrence choices have Persian labels; custom recurrence accepts Todoist's English date syntax, including its own date and time. In that mode the separate date and time controls are disabled; choosing a preset enables them again.

Saving a title or priority preserves the task's existing schedule. Changing the date or recurrence sends the new schedule. Clearing the date also clears time and recurrence. Delete and disconnect ask for confirmation in place. Completing a recurring task advances it to its next occurrence through Todoist's `item_close` command.

## Rescheduling

The owner approved `design/todoist/assets/reschedule.png` and requested the batch action shown in `design/todoist/assets/reschedule-all.png`. Unfinished tasks stay in Today after midnight. Timed tasks become overdue after their timestamp passes in the selected Widgetify timezone; date-only tasks become overdue after their day ends. The existing 30-second clock refresh and clock-correction listener update these states. Tomorrow keeps its day scope, and Upcoming still includes all active tasks.

`components/todoist-reschedule.tsx` supplies each overdue task's Change Date button and the Reschedule All button beside the overdue count. Both open the same shared PopoverMenu: Today, Tomorrow, or a custom date in the shared Jalali DatePicker with Save and Cancel. The batch menu shows the affected count and captures the IDs when opened. It changes only overdue tasks visible under the current project filter. Google events, completed tasks and tasks outside that filter are excluded. Cancel, Escape or clicking outside closes without starting a write. Once submitted, closing does not cancel an in-flight API command.

Rescheduling sends date-only `item_update` commands: content, projects, labels and completion remain unchanged. Each task retains its date-only or timed form, recurrence string, language and original recurrence timezone. Fixed timestamps keep their displayed clock time in Widgetify's timezone on the chosen local date, adjusting UTC across daylight-saving changes. Choosing Today can leave a timed task overdue when its retained time already passed.

The background reads the latest snapshot and skips selected tasks that were completed, deleted or lost their date before execution. Each batch command has its own stable UUID, derived from the operation and task ID. `src/services/todoist/sync-batches.ts` sends at most 100 commands per request, advances cursors with committed snapshots and stops after a command failure or account change. It commits confirmed partial results before reporting failure. Retry reuses the operation IDs, including after a lost response; writes never retry automatically. Failed updates keep their previous server state, and the UI never claims that a partial batch succeeded in full.

## Data and sync

The service domain is `src/services/todoist/`. The background worker serializes connection, sync and task commands across tabs. It synchronizes on browser startup, every widget mount in a new tab, reconnect after a network interruption and manual sync. An initial full sync loads active tasks, projects, sections and labels; later requests use the saved cursor and merge changes and deletion markers. Commands include unique ids and do not retry automatically. Retrying the same failed edit or completion in the open tab reuses its command ids, so a lost response does not create a second task or skip another recurring occurrence.

`todoistAccount` stores the token, task snapshot, cursor, last successful sync time and last error in local extension storage through the storage gateway. It is shared by tabs and watched for updates. Disconnect clears that account and its cached tasks. The app's existing Widgetify logout also clears local storage. A sync finishing after that clear does not restore the credential. Replacing the token closes open editors across tabs. The token is sent only as a bearer header to Todoist; it never enters query keys, analytics parameters or Widgetify server requests. Queries hold a token-free view.

A failed refresh preserves cached tasks and shows an error. An invalid token opens token setup. A rate-limit response records a cooldown from Retry-After. A timeout aborts the request after 20 seconds. A command failure does not claim success; the next sync reconciles the snapshot. Offline writes are not queued.

`hooks/use-calendar-completion.ts` reads and watches one local `todoistCalendarCompletion:` key per occurrence. Each key includes the Widgetify account scope, organizer, event id and occurrence start, normalized for fixed timestamp offsets. When supplied, Google's originalStartTime keeps a moved recurring occurrence hidden. Later recurring occurrences have separate keys. Each completion writes its own boolean, so completions in separate tabs cannot overwrite each other. Calendar rows wait for the initial storage read before appearing. Failed saves keep the row visible and show a storage error; read failures show rows and the same error. No calendar mutation request is sent. Logout or clearing extension storage clears these choices.

## Scope

This is a task widget, not the full Todoist client. It reads existing projects and sections; it does not manage projects, comments, reminders, attachments, collaborators or completed-task history. Todoist still applies the account's plan limits. It does not copy or merge tasks from Widgetify's existing task widget.
